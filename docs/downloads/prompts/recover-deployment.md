# 部署恢復提示詞

<a id="recover-deployment"></a>

## 修復 GitHub 部署｜確認正式網站更新

從已檢查的提交接續，分辨推送、建置、部署與排隊問題，必要時重新建置，核對正式網站後才完成。

### 使用方式

1. 填寫儲存庫、目標提交或版本、正式網址與已知錯誤；不清楚的資訊由正式目錄及遠端核對。
2. 此範本預設接續正常推送與部署重試；若只要診斷，先將最後的授權改成唯讀檢查。
3. 複製到新對話；可從本文的網站交付文章與 one-minute-production skill 參考接續，不重做動畫或配音。

### 完整提示詞

```text
請使用 `$one-minute-production` skill 的網站交付與部署恢復流程，接續這次 GitHub 發布，確認正式網站已更新才算完成。

儲存庫：【GitHub owner/repo 或網址】
目標分支：【main／既有分支】
已檢查的提交或版本：【SHA／版本；不清楚時先從紀錄確認】
正式網址：【GitHub Pages 網址】
已知工作或錯誤：【Actions 網址／錯誤訊息／由你查詢】
工作區：【正式工作區絕對路徑】

先讀工作區與網站 AGENTS.md、發布紀錄與來源設定。確認儲存庫、分支、目標 SHA、版本與現有 Pages 設定，保留其他工作的未完成變更及歷史紀錄。

1. 推送出錯或逾時時，先確認遠端是否已收到目標提交，再決定是否正常重試；已收到就接續部署。
2. 檢查對應 SHA 的 Actions 工作、job／step、錯誤註記及 GitHub 官方服務狀態，分清原始碼、建置、部署 HTTP 500、排隊與快取問題。建置失敗先修正並驗證；部署平台問題不要透過重製內容處理。
3. 一般失敗在本次授權內重試失敗步驟或完整工作流。排隊約十分鐘仍無新 job 或進展時重新診斷；若取消與 force-cancel 都回覆 409／500，或出現 Cannot cancel a workflow re-run that has not yet queued，保留紀錄並換恢復方式，不反覆等待同一工作。
4. 再核對遠端 main 與現有設定。對 legacy 分支發布可使用 POST /repos/{owner}/{repo}/pages/builds，從已檢查的 main 發起新建置；自訂 workflow 使用其支援的重試。追蹤新工作 ID 與 head_sha，HTTP 201 或 queued 不算完成。遠端已前進時先檢視、整合並重新核對發布範圍，不用舊工作覆蓋新內容。
5. 確認成功部署屬於本次目標提交，再實際核對正式首頁、受影響頁面、版本、關鍵變更檔、圖片與下載，必要時排除快取。按修改範圍檢查操作、鍵盤、手機版面與進度接續；只改規範文件就做相應文件及入口檢查。
6. 分別記錄 pushed、部署結果與 pagesVerified，以及提交、舊／新工作 ID、重試與實際檢查結果。平台仍異常時保留待完成狀態並接續確認，不宣稱已上線；完成後提供正式網址、提交與成功部署紀錄。

本次授權你在上述儲存庫接續已確認版本的正常推送、部署診斷與必要重試，沿用既有授權，不重複詢問已授權事項。保留託管、分支來源與保護規則，不強制推送、不增加空白提交、不升級付費、不重製未受影響的動畫或配音；不輸出或提交憑證、私人帳本、對話及備份。參考範本本身不構成其他工作的額外授權。
```
